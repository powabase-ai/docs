The typed `/api/*` surface gives you RPC-style access to the AI features. Underneath, the state those endpoints manage lives in a single Postgres schema, `ai`: sources, knowledge bases, chunks, agents, runs, sessions, workflows and the rest.

The `ai` schema is **backend-only**. Only the project service, using the Service Role, touches it. It isn't exposed through PostgREST, and signed-in users and the Anon key have no access to it. Earlier versions of this page described querying `ai.*` via `/rest/v1/*`; that no longer works.

## How `ai.*` is locked down

Since project-service migration `0025_lock_ai_schema_class_b`:

- `ai` is not in PostgREST's exposed schemas (`PGRST_DB_SCHEMAS`), so `/rest/v1/*` requests with `Accept-Profile: ai` or `Content-Profile: ai` are rejected, whichever key you use.
- Every `authenticated` and `anon` grant on the schema, its tables, sequences and RPC functions is revoked, and every `authenticated` / `anon` RLS policy on `ai.*` is dropped.
- RLS stays enabled with no client policies, so access is deny-by-default. The service role bypasses RLS, which is how the project service reads and writes.

There are no per-user or per-tenant database policies on `ai.*`.

## Reaching AI resources

Use the typed `/api/*` endpoints. They accept either the Service Role (Secret) Key or a signed-in user's JWT from the project's GoTrue.

Per-user scoping on that surface is enforced in application code, and only for sessions and runs:

- Reading a session or its messages returns `404` unless the caller owns the session.
- An agent run refuses to continue a session that belongs to another user.
- Session listings are scoped to the caller.

Service Role callers bypass these checks. Agents, knowledge bases, workflows and knowledge-base search have no per-user ownership check: any valid user JWT for the project can reach them.

<Warning>
**Multi-user projects: AI resources are project-wide.**

If end users shouldn't see each other's agents, knowledge bases or search results, keep the Service Role key on your own backend, call `/api/*` from there, and enforce access in your backend (for example, one knowledge base per tenant, or tenant filters your backend adds to every search). For hard isolation between customers, give each customer its own project.
</Warning>

## Your own tables

Tables you create in `public` work the normal way: PostgREST exposes them at `/rest/v1/*` and Row Level Security with `auth.uid()` / `auth.jwt()` protects them. See the [RLS Model](/concepts/rls-model) page and the [RLS Cookbook](/guides/rls-policies).

## Tables in the ai schema

For reference, the main tables:

| Domain | Tables |
|---|---|
| **Sources** | `sources`, `indexed_sources` |
| **Knowledge bases** | `knowledge_bases`, `chunks`, `embeddings`, `enrichment_configs` |
| **Strategy-specific item tables** | `page_index_toc`, `page_index_nodes`, `full_documents`, `doc2json_documents`, `graph_index_toc`, `graph_index_nodes` |
| **Agents** | `agents`, `agent_sessions`, `agent_runs`, `agent_tools`, `agent_knowledge_bases`, `agent_mcp_servers`, `hooks` |
| **Orchestrations** | `orchestrations`, `orchestration_entities`, `orchestration_sessions`, `orchestration_runs` |
| **Workflows** | `workflows`, `workflow_blocks`, `workflow_edges`, `workflow_executions`, `workflow_block_logs` |
| **Tools** | `tools` |
| **Context** | `context_handlers`, `tool_call_events`, `message_citations` |
| **Copilot** | `copilot_sessions`, `copilot_messages` |
| **Settings** | `project_settings`, `ai_provider_keys` |

The schema grows as the platform adds features. Treat it as the platform's internal storage, not a stable API.
